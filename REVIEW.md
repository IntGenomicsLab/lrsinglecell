# Review guide for LRSinglecell

Guidance for automated (Claude) and human PR reviews. The automated reviewer
only sees the diff and cannot run the pipeline or nf-test, so it must never
claim that tests pass or fail.

## Tests

- PR CI runs the pipeline nf-tests in `tests/` (`default`, `dna`,
  `lrkallisto`), tagged `pipeline`. `test_mixed` (cDNA + DNA in one run) has no
  nf-test: flag a change to the mixed-sample routing and ask for a
  `-profile test_mixed` run.
- Snapshot changes should match the code change. Unexplained md5 drift in
  unrelated outputs needs an explanation in the PR.
- Outputs that are not byte-reproducible (BAMs from `samtools sort`, lr-kallisto
  `bus/` and `counts_unfiltered/` EC-level files, MarkDuplicates metrics) belong
  in `tests/.nftignore`, so they are checked by name only. Flag a new
  non-deterministic output that is md5-snapshotted, and flag an ignore pattern
  that hides a deterministic output such as a count matrix.
- Changes to `bin/mark_dna_duplicates.py` should keep `tests/bin/` passing and
  extend it for new rules.
- Test data lives in `IntGenomicsLab/test-datasets` under `lrsinglecell/`;
  files there are never modified in place.

## Data types and routing

- Samples carry `meta.type` (`cdna` or `dna`) from the samplesheet and are
  routed with `.branch`/`.filter` on it. Check that new logic keeps `type` in
  `meta` across module and subworkflow boundaries (losing it publishes under
  `<sample>/null/...`), and that a DNA-only or cDNA-only run still works.
- `--quantifier` is only required when cDNA samples are present; DNA is
  aligned and deduplicated, never quantified.
- Barcode presets (`--barcode_format`) are mapped explicitly to flexiplex
  patterns and whitelists. A new preset needs its mapping for every demux
  path it supports, and lr-kallisto needs the barcode/UMI widths of each
  preset.
- Barcode and UMI tags (`CB`/`CR`/`XB`, `UB`/`UR`) have fixed meanings
  (corrected vs raw; `XB` keeps uncalled droplets separate). Check that
  grouping and deduplication use the right tag.

## Nextflow conventions

- Channels carry `[meta, data]` tuples; keep `meta` intact across joins and
  check that joins key on the right field and cannot pair records arbitrarily.
- Process-scope variables in `script:` blocks have no `def` prefix. Unused
  closure parameters are prefixed with `_`.
- Processes use resource labels (`process_single`, `process_medium`, ...)
  rather than hard-coded resources.
- A new step needs an entry in `conf/modules.config` (publishDir, `ext.args`);
  `versions.yml` should not be published.
- New or changed parameters are in `nextflow_schema.json`, with a `help_text`
  that matches the actual behaviour, and in `docs/usage.md`. On Nextflow 26 a
  CLI `--flag false` arrives as the string `"false"`; boolean logic should not
  make this worse.
- nf-core modules are installed/updated with `nf-core modules`, not edited in
  place under `modules/nf-core/`. Local changes belong in `modules/local/` or
  as an nf-core module patch.

## Containers

- Container directives keep the singularity/docker ternary used across
  `modules/`, with both branches pointing at the same tool version
  (depot.galaxyproject.org / `biocontainers/` pair).
- Images are pinned to a specific tag, never `latest`.

## Documentation

- `CHANGELOG.md` has an entry under the unreleased/`dev` version.
- New outputs are described in `docs/output.md`; new tools are cited in
  `CITATIONS.md`.

## Do not comment on

- Formatting that pre-commit/prettier fixes automatically.
- Files under `modules/nf-core/` and `subworkflows/nf-core/` unless the PR
  itself changes them.
- `ro-crate-metadata.json` churn (regenerated by nf-core lint).
- Template-sync PRs (`Template update for nf-core/tools ...`) beyond the
  conflict resolutions.
